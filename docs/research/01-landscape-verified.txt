
===== difficulty-calc
No existing calculator is enough on its own to back a per-skillset recommender, so combine them. osu!mania's official star rating (ppy/osu, MIT, calculator version 20241007) is one number from one Strain skill. It adds a per-column strain (constant 2.0 per note, x1.25 when the note sits inside a held LN, decay 0.125/s) to an overall strain (decay 0.30/s, with a small LN release bonus). It takes the peak of each 400 ms section and weights the sections by 0.9^i. It does not recognise patterns, so it cannot say which skill a map trains. The mania algorithm has not changed since the Oct-2022 update, and the 2026 Q2 release did not touch mania. The "Sunny rework" (sunnyxxy's Star-Rating-Rebirth, Feb-2025 paper) was proposed as ppy/osu PR #36342 by Natelytle. That PR was closed on 2026-02-22 "pending ongoing refactor work (Sunny rework is NOT CANCELLED)" and is not merged. You can only see its numbers on huismetbenen's WIP rankings. Etterna's MinaCalc (C++, MIT, calc version 527, July 2026) is the only mature calculator that outputs a skillset vector: Stream, Jumpstream, Handstream, Stamina, JackSpeed, Chordjack, Technical and Overall. It supports 4K/5K/6K/7K through keymode-specific "Ulbu" classes. Its input is only a row bitmask plus a time, so it ignores LNs entirely. It is already applied to osu!mania through minacalc-rs (MIT, wraps v515, parses .osu), Companella, osumania_map_analyser, etterna2osu and Ez2Lazer. Interlude's MIT-licensed prelude library has an explicit pattern recognizer and clustering system (pattern type, BPM, density percentiles), plus an existing pattern-similarity chart suggester that picks a rate. Quaver (MPL-2.0) classifies finger actions (roll, simple jack, technical jack, bracket) and weights LN layering, but outputs one rating. Recommended backbone: MinaCalc for the rice skillset vector, Sunny/SPM time-series channels for LN and release, and Interlude-style pattern clustering for labels you can show the player. The official SR is only for pp context. Start deterministic; add ML only for personalisation once there is score data.
-- RECS
 * Do not use the official osu!mania SR as the recommender backbone. It is one density-driven scalar with no pattern awareness. Use it only to show SR and pp (via rosu-pp or osu-tools).
 * Use MinaCalc (through minacalc-rs or your own FFI to upstream v527) as the rice skillset vector for charts: Stream, JS, HS, Stamina, JackSpeed, CJ, Tech. Pin a calc version and store it with every cached value, because MSD changes between versions.
 * Add an LN, release and inverse channel from the Sunny model's time series (Rbar, the LN-body term in Pbar, Jbar/Xbar), because MinaCalc ignores holds. Reimplement it from the paper rather than copying code, since the repo has no license. Alternatively evaluate SPMRating (MIT) against a held-out labelled set first.
 * Use Interlude-style pattern clustering (MIT prelude) for the concrete pattern labels you show players, such as '180 BPM jumpstream, 12% of chart', and port its Endless similarity scoring (BPM and density log-ratio, LN%, length, spikiness, rate rounded to 0.05) as the first recommender.
 * Build the player profile deterministically: per-skillset SSR from the player's own osu! scores (computed at the play's rate), aggregated with Etterna's erfc aggregate_skill. The recommendation target is skillsets where the player is more than X below their overall; pick charts whose dominant skillset MSD is 0.5-1.5 above the player's value at some rate in 1.0-1.3x.
 * Handle rates explicitly: compute features at 0.05 rate steps from 0.8x to 1.5x. Note in the UI that only NM, DT (1.5x) and HT (0.75x) are ranked on osu!, so custom-rate recommendations are practice-only (a rate-changed .osu copy, as Companella and osu!trainer do).
 * Treat ML as a later layer, not the core. Once you have a few thousand of the user's scores, fit a residual or collaborative model (opal-style NCF or IRT-like player-by-skillset x chart-by-skillset) to predict expected accuracy and correct calculator bias. Keep the deterministic calcs as interpretable features.
 * Validate against human labels, not against other calcs: use dan courses (Reform 4K, LN dans) and Etterna-rated packs as ordinal ground truth and report Spearman, as SPMRating does.

===== pattern-detection
Pattern detection in VSRG charts is already solved well enough by deterministic code, and every open-source implementation found uses rules rather than ML. There are three mature reference designs. (1) Interlude/Prelude (YAVSRG, F#, MIT outside interlude/) reduces a chart to a list of RowInfo primitives: the notes in the row, how many of them repeat a column from the previous row (Jacks), the direction the row moves, whether it rolls, the ms gap to the previous row and density. It then runs named pattern recognisers over that list with F# pattern matching: Stream/Chordstream/Jacks at the top level, then specific 4K and 7K types such as Jumpstream, Handstream, Jumptrill, Split Trill, Rolls, Trills, Minijacks, Longjacks, Chordjacks, Gluts, Quadstream and Brackets. Matches are grouped into BPM clusters within 5 ms/beat and the chart is labelled "X Hybrid/Tech/+SV". Companella (C#) and a Python port (LeoBlackMT) reuse this engine, and the Python port adds LN head/body/tail rows plus rules for Inverse, Release and Shield. (2) Etterna's MinaCalc (C++, MIT) takes only a per-row column bitmask and a time in seconds, cuts the chart into 0.5 s intervals and splits it into two hands (cols 0-1 and 2-3 for 4K). Per-hand col_type/base_type/meta_type sequencers feed about 30 "pattern mods" (JS, HS, CJ, OHJ, Roll, Anchor, RunningMan, etc.) that scale 7 skillsets. It ignores LN tails. (3) Quaver.API gives each lane a finger and a hand, classifies each finger's action (SimpleJack/TechnicalJack/Roll/Bracket), and defines LN layer types. Its QssPatternFlags enum lists 17 patterns, but the processor only ever sets Rolls and SimpleVibro. The ML papers found (Caronongan 2021/2023, Franks et al. 2023) estimate difficulty, not pattern labels. No labelled pattern dataset was found, so ML would have to learn from labels produced by rules, which is what Mug-Diffusion did by using MinaCalc skillsets as its pattern labels. Recommendation: use a deterministic rule engine for pattern labels and MinaCalc/rosu-pp for difficulty numbers, and keep ML for modelling the player (where a player is weak, predicting their accuracy), not for labelling patterns. For .osu files: column = clamp(floor(x*K/512), 0, K-1), K = round(CircleSize) when Mode:3, and a hold note is type bit 7 (128) with endTime in the extras field.
-- RECS
 * Use deterministic rules to label patterns. Port or reuse Prelude's recogniser design (MIT, about 350 lines in Patterns.fs) as the base and extend it. Put ML on the player side only (predicting accuracy or improvement on a pattern cluster from score history), and only once real score data exists.
 * Use a canonical row representation: {t_ms scaled by rate, tap_mask, ln_head_mask, ln_tail_mask, ln_hold_mask} as u16/u32 bitmasks, plus a derived per-hand col_type (left/right/jump, MinaCalc style) and per-column last-hit times. Get rhythm from gaps between rows (15000/ms gives 1/4 BPM), never from timing points.
 * Parse mania columns with clamp(floor(x*K/512), 0, K-1) and K = round(CS), keeping only Mode:3 maps. Do not do exact-x matching the way rosu-pattern-detector does. Treat type & 128 as a hold and read endTime from extras.
 * Take skillset numbers from minacalc-rs (MSD vectors for 4, 6 and 7 keys), and rosu-pp or Sunny/Star-Rating-Rebirth for LN-aware SR. Keep your own pattern labels as a separate layer, so a recommendation can say 'jumptrill at 190 BPM' and not just 'technical'.
 * Give LN work special attention. MinaCalc ignores LNs and Interlude does not label LN patterns. Use LeoBlackMT's inverse/release/shield rules as a draft and fix explicit ms tolerances.
 * Before trusting any thresholds, build a small hand-labelled validation set of chart sections (e.g. 200-500 windows across 4K and 7K). Every existing engine documents misclassifications at the boundaries (broken JS/HS as CJ, jumptrill as HS).
 * Make the thresholds configurable and scale them by rate (ms tolerance, minimum run length, snap limit). The community definitions (osu! wiki) have no numbers, and engines disagree.
 * Check licenses before copying code. prelude/ and MinaCalc are MIT, Quaver.API is MPL-2.0 (file-level copyleft), slider is LGPL-3.0, interlude/ is GPLv3, and Star-Rating-Rebirth has no license (ask the author).

===== existing-tools
Companella (leyna64/Leinadix, C#/.NET 8, osu!framework, MIT per its LICENSE file, last push 2026-08-07, v8.0.0 from July 2026) already covers most of what a "mania companion" usually promises. It has a rate changer, marathon creator, session tracker (memory reader plus .osr replay parsing), a skill trend panel across 7 MinaCalc skillsets plus overall, a session planner (warmup, ramp, main, cooldown curve), Interlude-derived pattern detection, a dan estimator (GradientBoosting to ONNX over MSD, Interlude and Sunny ratings), a manual section splitter, and a recommender with Push, Consistency, DeficitFixing and Skillset modes. The recommender is a simple deterministic heuristic, not ML. Each play is credited only to its map's dominant skillset. Skill per skillset is a weighted mean of MSD, weighted by recency (0.95^n) and accuracy ((acc-80)/20). Maps are then drawn at random from the LOCAL Songs folder inside a ratio band of that skill (for example 1.15±0.1 for Push), with KeyCount hard-coded to 4. Rate suggestions exist in the code but are commented out. Its replay timing deviations are never fed back into the skill model. So there is no pattern-level weakness diagnosis, no online catalogue, no automatic drill or section extraction, and no 7K or cross-VSRG support. Other tools: osu-trainer is only a rate/AR/OD/HP editor with no skill model, and has been stale since 2023/24. Tillerino is std-only collaborative filtering and closed. AlphaOSU does support mania: latent-factor embeddings for user×map×mod plus kNN pass probability, but its goal is pp farming and it has not been updated since 2024. osu-pps offers farm lists. osu!Skills and osu!Pulse are std-only. Etterna offers MSD skillsets, a rating aggregate and manual per-chart goals, but no recommender. Quaver has one difficulty number and pattern flags that are mostly unused. Interlude has the most relevant open code: a MIT-licensed pattern engine (Prelude) and a content-based "similar chart at auto-rate" suggester. Interlude also REMOVED its pattern-based skill ratings in 0.7.28.3. Overlays (tosu, osumania_map_analyser, Dan-Overlay) analyse maps, not players. The gap that remains is a pattern-level player model built from replay hit errors per detected pattern segment, feeding recommendations of specific maps, rates and sections from a large catalogue with a closed feedback loop. A deterministic, explainable algorithm should come first; ML is only justified later, for difficulty calibration or collaborative signals.
-- RECS
 * Do not rebuild Companella's recommender. It is a ~370-line heuristic of the form 'MSD band around a weighted mean', and cloning it adds nothing. Put your effort into a PATTERN-LEVEL player model. Segment each map with a pattern engine (port or reuse Interlude's MIT Prelude clustering), parse the replay (.osr or tosu precise hit errors), and compute per-segment judgement and accuracy against each segment's pattern type, BPM and density. The output is 'your accuracy on 1/4 jumpstream at 190 BPM drops to X%', which no existing tool produces.
 * Start deterministic, not ML. A Bayesian or Elo/IRT-style per-pattern ability estimate is explainable and works with little data. Model P(hit segment at acc ≥ target | ability_pattern, difficulty_segment). A 1-parameter logistic IRT or a Glicko update per (pattern, BPM bucket) works. Add ML only when real data shows the need: for example a learned difficulty correction per segment, or a collaborative signal in AlphaOSU's embedding style once enough users opt in.
 * Use a large online catalogue, not just the local Songs folder. Precompute pattern and MSD indexes for ranked, loved and popular graveyard mania maps (osu! API v2 plus a mirror for .osu files; check the ToS and rate limits separately). Recommend maps the user does NOT have, including the target rate and the exact timestamps of the relevant section. Companella and Interlude only search the local library.
 * Generate drills automatically. Companella's Difficulty Splitter needs manual markers. Your version should auto-extract the weakest-pattern sections into practice .osu files, with auto-rate chosen by density matching, as Interlude's Endless.fs does. Use Companella's rate pipeline or osu-trainer/cosutrainer as the reference.
 * Cover what Companella leaves out: 7K and LN pattern taxonomy (inverse, release, shields, LN density), osu!lazer via tosu, and cross-VSRG ingestion (Etterna XML/replays, Quaver .qua via Quaver.API (MPL-2.0), StepMania .sm/.ssc, BMS). Linux support is another gap, since Companella is Windows-only.
 * Use tosu's websocket as a separate process instead of linking a memory-reader library. This keeps your license choice free (tosu is LGPL-3.0, gosumemory is GPL-3.0) and gives you both stable and lazer.
 * Build a closed-loop evaluation from day one. Log which recommendation was shown, whether it was played, and how the per-pattern ability moved over the next N sessions. None of the surveyed tools measure whether their recommendations actually improve skill. That is the only defensible way to later decide whether an ML model beats the heuristic.
 * Learn from Interlude removing its pattern-based skill ratings (0.7.28.3). Show uncertainty (confidence intervals, a minimum sample count per pattern) and avoid presenting a single 'jack skill number' that comes from 3 plays.

===== data-sources
Bottom line: build the companion local-first. The osu! API v2 cannot supply the training history a skill model needs. For player history, GET /users/{id}/scores/best stops at the top 200 plays: osu-web caches 200 IDs and says "we're not supporting beyond 200". scores/recent only returns the last 24 hours. The terms of use prohibit "harvesting mass score/user/beatmap data" and set a limit of 60 requests per minute. For mania, difficulty attributes are only star_rating and max_combo, so skillset data has to be computed locally from the .osu files (MinaCalc/MSD, rosu-pp). Rate practice on stable produces rate-edited .osu files. Their MD5s are not submitted, so those plays only exist in local data: scores.db and the replays in Data/r and Replays for stable, and client.realm plus the hashed files/ folder for lazer. Pattern-level diagnosis needs per-note timing, which only replays provide. The .osr format stores the mania key bitmask in the frame X field. tosu reports hit counts and a hitErrors array, but the errors are not tied to columns or notes, so it is useful for session detection and not for pattern diagnosis. For a map catalogue and offline model training, data.ppy.sh publishes monthly mania dumps. The 2026-09-01 top 10000 dump is about 1.9 GB bz2 and the random 10000 dump about 448 MB. Both include a new `scores` table whose JSON holds perfect/great/good/ok/meh/miss and mods, plus an osu_files dump of every ranked .osu (about 1.43 GB). The licence forbids production use without contacting ppy. For downloads, nerinyan (v3, healthy, with a cs_min/stars/mode filter) and osu.direct (120 requests per minute without a token) are free. catboy.best/Mino rejects requests without a user-agent that identifies the app. BeatConnect's API needs a Patreon subscription. The official download endpoint is lazer-only. Recommendations can appear in-game on stable by writing collection.db, which is what Companella does, with a backup and an osu! restart. Lazer keeps collections inside the Realm database (BeatmapCollection.BeatmapMD5Hashes), and there is no safe documented way to write to it from outside. For cross-game data, EtternaOnline has an undocumented public JSON API. It returns per-score skillset SSRs, judgements and rate, which makes it a useful source of labelled data. Quaver has a documented v2 API limited to 100 requests per minute.
-- RECS
 * Build the data layer local-first. On stable, read osu!.db (maps, key count, OD, MD5), scores.db (all attempts, including rate-edited maps) and replays in Data/r and Replays. On lazer, read client.realm through the Realm .NET SDK plus the hashed files/ folder, and treat it as read-only. The osu! API v2 cannot replace this: best plays stop at 200, recent covers 24 hours, and bulk harvesting is banned.
 * Use the osu! API v2 with the Authorization Code grant (identify+public) only to link the user and to resolve MD5 to beatmap ID (/beatmaps/lookup, /beatmaps?ids[] in batches of 50). Also use it to backfill the top 200 bests and to poll recent plays with include_fails=1 no more than once a minute per user, with backoff. Cache everything locally (SQLite).
 * Precompute the recommendation catalogue offline from the data.ppy.sh osu_files dump. Filter mania maps by key count and run MinaCalc (MSD per skillset at rates such as 0.8–1.5x) plus a pattern detector over them. Before distributing any derived data or model, email contact@ppy.sh, as the licence requires.
 * Use the mania_random_10000 dump's `scores` JSON (the judgement statistics) together with EtternaOnline per-score SSRs to fit or validate the player-skill model. A deterministic baseline comes first: take each player's skillset rating as a weighted top-N of MSD×accuracy-adjusted performance, as Etterna does. Add ML only for residuals, such as predicting accuracy on an unseen map from its pattern vector.
 * Store per score: map MD5, rate (clock_rate from DT/HT, or a lazer speed_change setting, or a rate-edited copy that has been mapped back to its source map by metadata and hit-object hash), full judgement counts (MAX/300/200/100/50/miss), pass or fail, and timestamp. Where a replay exists, also store per-note hit errors aligned to the .osu, so weaknesses can be assigned to patterns (jacks, JS, HS, LN releases) rather than only to whole maps.
 * Use tosu as an optional, pluggable live source for play-start and play-end triggers on both clients and under Linux/Wine. Do not rely on its hitErrors for pattern diagnosis; parse the replay after the play instead. Avoid linking ProcessMemoryDataFinder unless the whole app can be GPL-3.0.
 * Deliver recommendations on stable by writing a dedicated collection to collection.db: back up the file first, write only while osu! is closed, and offer a restart. On lazer, do not write realm. Offer a generated .osz or an export and import flow, or show the list in the app with direct links.
 * Put downloads behind a mirror abstraction with fallback: nerinyan, then osu.direct (respect 120/min and Retry-After), then catboy.best with an identifying User-Agent such as 'AppName/1.0 (+repo url)'. Make BeatConnect optional for users who have a Patreon token. Never scrape osu.ppy.sh download pages with session cookies.

===== recsys-ml
You don't have to pick between "AI" and "an algorithm". The choice that matters is what data you can legally get. A companion app like Companella or osu!trainer reads the player's own local scores and replays. That makes the setup single-user. Methods that learn from many players are out: collaborative filtering (CF), neural CF, deep knowledge tracing (DKT) and transformer embeddings all need large score sets from many players. The osu! API v2 terms forbid mass harvesting of scores. The data.ppy.sh dumps say "Permission is NOT implicitly granted to deploy this in production use of any kind." So CF recommenders like AlphaOsu (ALS + Bayesian ridge, supports mania) and opal (NeuMF on the top-10K mania dump) are research references, not a foundation you can ship on.

The strongest architecture for a solo developer has three layers:
1. Deterministic chart analysis. Use MinaCalc/MSD skillsets through minacalc-rs for 4K, Sunny-style strain for 7K and LN, and Interlude's MIT-licensed pattern recognisers to tag passages.
2. A small statistical player model fitted to the user's own scores. Options: Elo/Glicko with an uncertainty value per skillset (as Lichess does for puzzles), a one-parameter IRT/logistic model, or Etterna's own aggregate_skill fixed-point. Each score is treated as player vs chart-at-rate.
3. A target-difficulty rule. Recommend chart and rate pairs whose predicted accuracy sits just below the player's goal (challenge-point framework), limited to the weakest skillsets.

Rate is a continuous difficulty knob, which fixes most cold-start and "no map at the right level" problems. Replay hit-error analysis per column and per pattern gives much more signal than final scores.

Education research backs simple models. Bayesian IRT matched or beat DKT in Wilson et al. 2016, and Elo is cheap and works well for adaptive practice (Pelánek 2016). An LLM has a legitimate but narrow role: turning structured, already-computed results into readable explanations and coaching text. It is a bad fit as the recommender itself, because it fabricates items and cannot compute chart difficulty.
-- RECS
 * MVP: build a deterministic content engine plus a small statistical player model, not 'AI'. Content: MSD per skillset per rate from minacalc-rs for 4K; Sunny-style SR (Daniel/SPMRating) for 7K and LN; Interlude-style rule recognisers to tag passages with patterns. Player: one latent skill value θ per skillset, fitted to the user's own local scores (osu! stable scores.db or lazer, plus replays). Use a logistic or 1PL-IRT link that predicts accuracy from (θ_s - MSD_s(chart, rate)), or reuse Etterna's aggregate_skill directly. It runs in milliseconds, works offline and can be fully explained.
 * Track uncertainty from the start. Use a Glicko-style deviation per skillset, or a Bayesian logistic posterior, and show 'insufficient data' instead of confident recommendations. Handle cold start by importing the user's existing top or local scores and showing a short placement set of about 5-8 charts, one per skillset, at graduated rates.
 * Recommendation rule (challenge point): among charts the user has or can download, pick (chart, rate) pairs where the target skillset is dominant in the MSD vector and predicted accuracy is slightly below the user's goal. Expose that target as a user-tunable setting; don't hard-code 85%. Prefer changing the rate over finding new maps; it is the cheapest difficulty knob and avoids the 'no map at my level' problem.
 * Recommend patterns, not only maps. From replays, compute hit-error and misses per tagged passage (jumpstream sections, chordjacks, LN releases, and so on). Estimate a per-pattern weakness (a Beta-Binomial or logistic rate per pattern tag is enough), then pull charts or sections dense in that tag. That answers 'what specific pattern should I train' with a few replays and no population data.
 * Phase 2, once you have months of a single user's history: move to multidimensional or explanatory IRT (item difficulty = weighted sum of pattern-feature densities, with learned weights) and add recency weighting or a random-walk drift in θ so the model follows improvement. A hierarchical Bayesian fit (PyMC, Stan or NumPyro, offline) is still cheap at this scale.
 * Phase 3, only with legal data: collaborative filtering or opal-style embeddings require either written permission from ppy (contact@ppy.sh) for dump-derived models, or opt-in anonymous score telemetry from your own users. Do not scrape the API; it is explicitly prohibited and risks token revocation.
 * LLM role: optional explanation layer only. Pass it structured facts (skillset deficits, the chart ID and rate the engine picked, predicted accuracy, per-pattern error stats), restrict output to IDs from your database, and use it for coaching text or session summaries. Never let it choose maps or estimate difficulty.
 * Evaluation: log predicted vs actual accuracy for every play (calibration and MAE). This is the only honest test of whether the model works. 'Did the user improve faster' cannot be proven without controlled comparisons, so be modest in claims.

===== training-pedagogy
The osu!mania and VSRG communities train with a stable, shared model that a recommender can copy. Skill breaks into pattern families (skillsets). You measure it with tiered test courses (dans) and with per-skillset difficulty scores. You train it with targeted packs, rates and good session habits. For 4K the vocabulary is well standardized. The osu! wiki pattern pages (Stream, Jack, Chord, Trill, Anchor, Hold note) and Etterna's 8 MinaCalc skillsets (Overall, Stream, Jumpstream, Handstream, Stamina, Jackspeed, Chordjack, Technical) both use it. So do the Reform, Shoegazer and Signicial dans, which test Jack / Technical / Speed / Stamina at 96% accuracy. 7K dans (Jinjin) split into Regular (jack/tech/speed/stamina) and LN (LN/tech-LN/inverse/release) at 96% and 95%. Guides agree on a few points. Skill transfers by pattern and by technique: playing a pattern improves similar patterns, and manipulating a pattern trains only the manipulation. Your weakest skillset limits your scores. A skill 'rusts' after about a week without play. Reading and finger technique are separate causes of speed walls. Rates (0.7x-2.0x) are the main tool for fine-tuning difficulty. Long sessions, tilt and chasing improvement make progress worse. MinaCalc defines MSD as the difficulty at a 93% Wife (J4) score and computes it per rate from 0.7x to 2.0x. That gives a ready-made axis for push, consistency and weakness recommendations. Companella already does exactly this. Hard gap: MinaCalc gets only tap rows, and LN holds and releases are dropped before the calculator sees them. It is also built for 4K; 5K-7K support exists but scales values from the 4K model. So LN (inverse/release/hybrid) and 7K need their own pattern features. On AI vs algorithm, the pedagogy supports a deterministic core first: pattern detection plus per-skillset ratings plus rules for push, consistency and weakness fixing. ML (for example, predicting a score from a player's history and a map's features) can come later, once there is play data. The taxonomy must be explicit and explainable, because players think in these named categories.
-- RECS
 * Use a two-level taxonomy. Level 1 (4K): the 8 MinaCalc skillsets plus 4 LN skillsets that MinaCalc lacks: LN-Inverse, LN-Release, LN-Hybrid/Coordination and LN-Density. Level 2 (patterns): osu!wiki / VSRG-wiki leaf labels such as roll, burst, light/dense JS, HS, quadstream, jumptrill, split trill, anchor, minijack, longjack, light/dense CJ, speedjack, polyrhythm, grace, broken stream, shield and release. Recommend at the skillset level, and explain and filter at the pattern level.
 * Build the core as a deterministic engine first. (1) A rule-based pattern detector over note rows: column overlap between adjacent rows, chord size, interval/BPM, run length, anchor ratio, and LN coverage/release variance. (2) MSD per rate from MinaCalc for 4K taps. (3) Player skill per skillset from their scores (Etterna-style aggregation of score-specific ratings). (4) Rules with the four community modes: Push (map at about +0.5-1.5 MSD above the skillset rating), Consistency (at or below the rating, with an accuracy target), Deficit (lowest skillset relative to Overall), Rust (a skillset not played in 7+ days). Consider ML only for score prediction once you have per-player histories.
 * Treat rate as a first-class recommendation output (map + rate), not just a map ID, because the pedagogy relies on rates. Generate rate files for stable, as Companella and osu-trainer do. On lazer, warn that custom DT/HT speed is unranked.
 * Encode the session template the community already uses: warmup (SS-able, then 99% maps, on the skill to be trained) → ramp-up → main block (target weakness, push or consistency) → cooldown or fun maps. Cap at about 60-120 min, and suggest a break when accuracy drifts within a session (a fatigue signal).
 * Diagnose speed walls as reading vs technique with controlled comparisons. Accuracy falling with note density at a fixed rate suggests reading; accuracy falling with rate on low-density familiar patterns suggests technique. This is a design inference, not a sourced rule, so check it against real play data.
 * Use the dan ladders (Reform 4K, Signicial, 7K Jinjin Regular/LN, 4K LN dans) as external checkpoints and calibration labels. Map each dan stage's maps to MSD and pattern vectors so the app can say 'you are about Reform 6th in Jack, 4th in Stamina'.
 * Do not promise technique coaching from score data. Manipulation, vibro vs wrist-jack, and jumptrilling rollwalls cannot be seen in accuracy numbers. Say so in the UI, following the Windoze and midgy guides.
 * Make accuracy targets adaptive to the player's current consistency, not a fixed 96%. Follow the community warnings against pushing accuracy too early.

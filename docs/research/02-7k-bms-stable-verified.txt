
===== 7k-difficulty-patterns
The osu!mania SR you would compute for 7K is the same on stable and lazer. Stable 20231217.1 changed its local difficulty calculation to the lazer code ("Update osu!mania difficulty calculator"), and every mania change since then has been a refactor with no effect on values (PR #35029: "no actual changes to difficulty or performance"). rosu-pp is a precise port of lazer, so for ranked 7K maps it should match stable/web SR, apart from tiny floating-point differences in release builds. The lazer mania calculator knows nothing about patterns. It adds a per-column strain (constant 2.0, ×1.25 while another hold is active) to a global overall strain that decays with time, plus a logistic bonus for awkward LN releases. It has no concept of hands, trills or brackets. That explains the long-standing 7K complaints: low-density 7K is underrated, dense chord and LN charts are inflated, and brackets and minijacks are underrated.

The only serious community rework is sunnyxxy's "Star Rating Rebirth". It is keymode-generic, has an explicit 7K cross-column coefficient vector, and its parameters were tuned by hand after an ML-fitting attempt was dropped. ppy has not merged it. It can be used standalone: Python (repo has no license), C# (MIT), or Rust through Metron (MIT, crate metron-rs).

Etterna MinaCalc (v527 on master) has a real 7K module, but it is thin: only 4 generic pattern mods, the middle column is assigned to the left hand with a "FIND SOMETHING BETTER" comment, and most skillsets are scaled by 4/7. minacalc-rs (MIT crate, v515) accepts 4, 6 and 7K. Interlude (prelude is MIT) has 7K pattern recognisers: Brackets, Double Stream, Dense/Light Chordstream and jacks, with no 7K rolls or trills yet. Its hand split puts 4 columns on the left hand. Quaver marks the middle lane as Ambiguous/Thumb and averages two solves, one assuming each hand. BMS tools use tables instead of formulas: beatoraja stores only density stats, and walkure.net fits an IRT graded-response model to LR2IR play data. For your app, IRT is the strongest precedent for recommending maps from a player's results.
-- RECS
 * Use rosu-pp (Rust, MIT) for the 'official' SR shown to users. It matches stable for native 7K maps because stable has used the lazer calc since 20231217.1. Do not use it as a skill model, because it cannot see patterns.
 * Compute Sunny SR components (J̄, X̄, P̄, Ā, R̄, C, Ks) per time window as continuous features. Take them from Metron or your own Rust port, validated against the Python reference and zzzzv's C# port. The Python repo has no license, so implement from the paper or use the MIT ports.
 * Build the pattern detector as a deterministic rule engine over row bitmasks (7-bit u8). Port Interlude's SPECIFIC_7K recognisers (MIT) and MinaCalc's is_bracket and base-type rules (MIT), then add the missing 7K classes: rolls/stairs, trills with one-hand, two-hand and thumb tags, jumptrill vs split trill, thumb metrics, hand balance, and LN shield/inverse/release.
 * Make the hand map a user setting (3-1-3 thumb default; 4-3; 3-4; both thumbs) and compute hand-dependent features under it. Following Quaver, optionally average over the two hand assumptions when the setting is 'auto'.
 * Answer to 'AI or algorithm': ship deterministic analysis (SR, Sunny components, pattern tags) and use a statistical player model rather than deep learning. Fit an IRT/Elo-style model per pattern skill from the user's own scores (accuracy vs pattern-tagged difficulty), as walkure does for BMS, and recommend maps where P(success) is about 0.5–0.7 on the weak skill. Sunny's author also dropped ML fitting in favour of hand-tuned parameters, and deep models need labeled 7K data that does not exist at scale.
 * Calibrate 7K skill levels against Jinjin's 7K Regular and LN dan courses (0–10, Gamma to Stellium). They are the only widely accepted labeled 7K skill anchors.
 * Treat MinaCalc 7K MSD only as an optional secondary signal. It uses 4 pattern mods, assigns the middle column to the left hand, and rescales output by 4/7. minacalc-rs is pinned to 515 while Etterna master is 527.
 * Keep LN analysis separate from rice analysis. Community complaints and the dan system both treat 7K LN as a distinct skill, and osu!'s LN bonus (holdFactor 1.25 plus logistic release addition) is known to inflate LN charts.

===== 7k-pedagogy-tables
For 7K, both osu!mania and BMS/IIDX already have curricula you can build on, and BMS/IIDX also has proven statistical methods for recommending charts. On the osu! side, Jinjin's 7K Dan Courses are the de facto standard. They run 0th–10th plus Gamma, Azimuth, Zenith and Stellium, in two tracks: Regular and LN. Each dan has 4 maps, and each map slot always tests the same skill. Regular: jack, tech, speed, chordstream stamina. LN: general, tech, inverse, release. You pass with 96% (Regular) or 95% (LN), with no pausing except in the breaks between maps. Most dan sets are Loved, so they have leaderboards. KomeijiDove split every dan into single-skill practice sets, which gives a ready-made difficulty ladder for each skill. Other sources: tyrcs' harder Wild 7K Dan (I–IX, updated 2025), a pack whose difficulties are named by pattern (the 7K Road to Gamma Dan Pack), and 5ynt3ck's 6,262 osu! conversions of charts from 8 BMS difficulty tables, each carrying its table level. On the BMS/IIDX side, the lists of charts sorted into difficulty levels share one JSON format: header.json points to a data file of charts keyed by md5, each with a level. Satellite and Stella train 地力 (base skill). Specialised lists train single skills: chords, delay, scratch, LN and vertical jacks. The IIDX community's split between 地力 and 個人差 (individual-difference, pattern-specific) charts has a statistical form. In item response theory (IRT) it is the discrimination parameter of each chart; CPI measures it as the inverse of the logistic slope. walkure.net fits a graded response model to LR2IR clear data from about 20,000 players, estimated with MCMC. It recommends charts by the probability of improving the player's clear on that chart, but it explicitly ignores personal strengths and weaknesses. CPI uses Elo ratings plus a logistic regression per chart. Tachi's Sieglinde fits player skill and chart difficulty from clear data, anchors them to the lists' existing levels, and pulls charts with few plays back toward their listed level. Recommendation: use a hybrid, not deep learning. Tag patterns deterministically, then fit a multidimensional IRT/Elo model over osu! 'lamps' (clear levels defined by fail/pass/95%/96%/etc.), with Jinjin's 8 skill slots as the first skill axes.
-- RECS
 * Use a hybrid system, not an end-to-end AI model. (1) Deterministic pattern tagging on .osu files: jack/chordjack, bracket/tech, stream/speed, chordstream stamina, LN general/tech/inverse/release, rice/hybrid/LN balance. (2) A statistical skill model (IRT/Elo) over the player's results. This is what walkure, CPI and Sieglinde do, and they work with far less data than deep learning needs.
 * Define osu! 7K 'lamps' as ordered result levels so a graded response model applies: FAIL < PASS < 95% (LN dan / S) < 96% (Regular dan) < 97% < 98%+. Give each chart a discrimination a (地力 vs 個人差) and one threshold b per lamp, as walkure does.
 * Make skill multidimensional, the part walkure explicitly lacks. Use a global θ plus one θ_k per axis, with chart loadings on each axis coming from the pattern tagger. Start the MVP with Jinjin's 8 slot axes (Regular: jack, tech, speed, stamina; LN: general, tech, inverse, release) plus Rice/LN/Hybrid from MWC.
 * Seed chart difficulty from existing curated ladders and pull toward them when data is thin, as Sieglinde does: Jinjin dan position, KomeijiDove per-skill ladders, BMS table level on converted charts, and star rating as a weak prior. Blend in the data-driven estimate with a confidence weight based on play count.
 * Recommend charts at a target success probability (about 40–70%, walkure's 50% point), weighted by discrimination: easy charts with high a to confirm skill, hard charts with low a as stretch attempts. For weakness training, pick charts that load heavily on the lowest θ_k with b near that θ_k.
 * Build a short placement test from high-discrimination charts spread across difficulty, using the KomeijiDove single-skill ladders. Choose the charts by AUC/information, as rice_Place did (5 charts, AUC 0.904), so users are not forced through full dan runs.
 * Publish curated 7K training lists in the BMS table JSON format (header.json + data.json; osu! beatmap MD5 as key; levels; courses with accuracy/constraint rules). Community lists can then be shared, and the Go/Java parsers serve as references for a Rust implementation.
 * Handle the known estimation biases: ignore unplayed charts; do not let old weak results on easy charts drag θ down indefinitely (decay by recency); note that 'no attempt' is not 'fail'; and remember the osu! API shows only top scores, so read the player's own stable score database for fails and attempts.
 * Curriculum order for 7K: Normal Kyu axes (singles rice → hybrid → chord rice → LN) → Regular and LN dans 0–3 → 4–8 → 9–10 → Gamma+. Add specialised single-skill packs when one θ_k lags. This mirrors the BMS advice: Satellite/Stella for 地力, specialised lists for weaknesses.

===== skill-model-irt
Every serious VSRG skill system I found is a small parametric model, either a latent-trait (IRT/Elo) fit or a deterministic response function. None of them is a black-box ML model.

- **BMS/IIDX (walkure, ereter, Sieglinde, rice_Place):** walkure fits a Graded Response Model to clear lamps: P(lamp ≥ k) = σ(a(θ − b_k)). Sieglinde fits skill and difficulty jointly by gradient descent. rice_Place builds Elo from head-to-head lamps, then runs a logistic regression per chart. Recommendations come from P(next lamp | θ).
- **Etterna (MinaCalc):** this is a deterministic response function per time interval. A player of skill x keeps pts·(x/d_i)^p points on an interval of difficulty d_i (p = 1.7 to 2.0). SSR is the smallest x that reproduces the achieved accuracy (capped at 96.5%). Each skillset is the erfc aggregation of the top SSRs (×1.05), and Overall is now the plain mean of the 7 skillsets.

**What this means for osu!mania stable 7K**
- Pass/fail is a weak and incomplete signal. scores.db stores only completed plays. However, API v2 `recent` with `include_fails=1` does return fails, but only from the last 24h. That corrects the premise that the API exposes only passed or best scores.
- The strongest signal is the per-note timing timeline, from local replays (.osr) or a live memory reader (tosu). It gives per-pattern evidence and is the only thing that properly separates multiple skill dimensions.

**Recommended model**
- **Chart side:** per-window, per-pattern difficulty from a deterministic 7K analyzer. Sunny/SPM-style strain calculators are the prior art; Sunny has no license, so reimplement it rather than copy it.
- **Player side:** a per-skill latent vector θ_k fitted by MAP with a hierarchical prior. The prior is θ_k = θ_global + δ_k, with θ_global taken from the API's 7K pp. Update it online (Elo/Kalman-style) after each play.
- **Recommendation:** P(success | θ, chart), where success means reaching a target accuracy. Use windows that depend on the mode: about 0.85 to 0.95 for warmup, 0.6 to 0.8 for training, 0.4 to 0.5 for push. Add a pattern-purity weight and an information-gain term.

**ML vs algorithm, and the LLM:** gradient boosting or neural nets only make sense for calibrating chart difficulty against human dan labels. A solo local app cannot train a player-outcome model because it has only one player's data. An LLM should only explain results and parse the user's goals; it should never estimate anything.
-- RECS
 * Treat 'AI vs algorithm' as a false dichotomy. IRT and Elo are small statistical models (logistic regression with latent factors). Build a Bayesian parametric model with about K+1 parameters per player (fitted by Newton/MAP in Rust in microseconds), not a gradient-boosting or neural player-outcome model. A local single-user app has no population data to train one, and public API data is selection-biased (best passes only).
 * Ingest data from 4 sources, in order of value: (1) tosu sidecar for every attempt, including fails and quits, with live judgements and hit errors. (2) Re-judged local .osr replays for per-note offsets on past plays. (3) scores.db for completed plays (judgement counts and mods). (4) API v2 recent with include_fails=1, polled at least every 24h, plus the 7K variant pp for the prior. Drop or down-weight plays with the Random or Mirror mods for pattern attribution, and handle rate changes (DT/HT or rate-edited .osu files with a new MD5) as separate chart variants.
 * Use custom accuracy (MAX=320, 300, 200, 100, 50) or a Wife3-style continuous per-note score from hit offsets as the outcome. Do not use pass/fail as the primary signal: mania HP is lenient and NF is common. Define 'success' on a chart as reaching a user-chosen accuracy goal A*.
 * Chart side (deterministic): split each 7K chart into windows (about 1s or per measure). Compute per-window pattern labels (a 7K taxonomy to define, for example stream, jumpstream, handstream, chordjack, jackspeed, trill/bracket/split-hand, LN release, stamina/density) and per-window difficulty d_{w,k}. Reimplement Sunny/SPM-style strains; do not copy the unlicensed Sunny code.
 * Player side MVP (Etterna-style): per play, invert the per-window point-loss model (kept = (θ/d)^p) to get a per-skill performance rating using only the windows labelled with skill k. Aggregate with Etterna's erfc top-score aggregation. This works from about 5 to 10 plays and is fully explainable.
 * Player side V2 (Bayesian, multidimensional): θ_k = θ_global + δ_k, with θ_global ~ N(prior from the API 7K pp), δ_k ~ N(0, τ²) and optional skill correlations. Use a non-compensatory, weakest-link likelihood per window (window accuracy depends on the dominant skill's θ − d). Fit by MAP, never plain MLE: walkure-offline's MLE fails when a player has all successes or all failures. Update online after each play with an MERS/Elo- or Kalman-style step, plus variance inflation over time to model skill drift.
 * Chart selection: compute P(success | θ, chart). Filter by a mode-dependent window: warmup/consistency 0.85–0.95, training about 0.6–0.8 (default 0.7), push 0.35–0.5. Score candidates by pattern purity (share of the chart's difficulty mass in the target skill k) × closeness to the target P × an information-gain bonus for high-uncertainty skills (Thompson sampling works). Include walkure-style 'reverse recommend' for goals already met with P < 0.5 (lucky or unstable results worth re-verifying). Log realized success rates and recalibrate the slope a and the target window.
 * Use ML only for chart-side calibration: a monotone-constrained gradient-boosting or ridge model mapping handcrafted pattern and strain features to human dan labels (Leo_Black benchmark; 7K dan courses). Validate with Spearman correlation and MAE against held-out labels.
 * LLM role: optional and outside the estimation loop. Use it to turn free-text goals into structured filters (for example 'quiero mejorar chordjacks' becomes skill=CJ, mode=training), write natural-language session plans and explanations from the model's numbers, and summarize progress. Never let it choose charts or estimate probabilities.
 * Validate before shipping: hold out the player's latest N plays and compare log-loss and Brier score (or accuracy RMSE) of the Bayesian model against the Etterna-style baseline and a simple SR-only baseline. Adopt the multidimensional model only if it beats SR-only on this player's data.

A Tauri 2 companion app for osu! stable 7K can be built almost entirely from maintained Rust crates. Only a few pieces need custom code. Parse and analyze maps with rosu-map (MIT, 0.2.1). Get difficulty with rosu-pp 4.0.1 (MIT, April 2026), which covers mania, accepts any clock_rate from 0.01 to 100, and has lazer(false) for stable. Etterna-style skillset MSD comes from minacalc-rs 515.2.0 (MIT), which says it supports 4K, 6K and 7K. Read and write the stable databases with osu-db, pinned to exactly 0.2.1. That is the only release with the 20250107 osu!.db change (star ratings stored as Int-Float instead of Int-Double). crates.io still serves the unyanked, older 0.3.0 (2021) as the "latest" version, so a plain `cargo add` picks the wrong one. Get live game state from tosu, an external app (TypeScript, LGPL-3.0, v4.26.2 on 2026-09-04, has a Linux build that reads osu! under Wine), through its /websocket/v2 API. tosu does not give per-column mania key state: its key overlay only has k1/k2/m1/m2. Per-column analysis therefore has to come from the local replays in Data/r. In mania replays the x field is a bitmask of held columns, and osu-db can decode them. For rate-changed maps, copy osu!trainer: scale every time in the .osu, time-stretch the audio (it uses SoundStretch, i.e. SoundTouch), pack a .osz and open it with the shell so osu! imports it. In Rust that means soundtouch (LGPL-2.1), ssstretch (MIT, Signalsmith) or an ffmpeg sidecar (atempo, range 0.5–100). Only write collection.db while osu!.exe is closed, because osu! rewrites it on exit. For the online side, use rosu-v2 (MIT; crates 0.11.0, git active 2026-09-27), the official 60 requests/minute limit, and mirror downloads, since the official download endpoint needs the lazer scope. The monthly data.ppy.sh dumps (all ranked .osu files, about 1.4 GB, plus top-10k mania scores) are the best offline dataset for building a local map index and training anything learned later. WSL2 is a VM, so it cannot read memory of a Windows osu! process. Real integration testing has to run on Windows or on Linux+Wine.
-- RECS
 * Architecture, MVP: a Tauri 2 app whose Rust backend has five modules. (1) `game_link`: tokio-tungstenite client to tosu ws://127.0.0.1:24050/websocket/v2. Use state, beatmap.checksum, folders.songs and resultsScreen. The user installs tosu separately, so there is no licence coupling and no custom memory reading. (2) `library`: bootstrap from osu!.db with osu-db pinned `=0.2.1`, then keep your own SQLite index (rusqlite) of 7K maps keyed by MD5, refreshed by a notify watcher on the Songs folder. (3) `analysis`: rosu-map to columns and times, a custom pattern extractor, rosu-pp with lazer(false) and clock_rate for SR/strains, and minacalc-rs for MSD skillsets. (4) `sessions`: scores.db plus a watcher on Data/r replays decoded with osu-db. Rebuild per-column timing error by matching the x column bitmask against the chart. (5) `generator`: a line-level .osu time-scaler plus symphonia → soundtouch or ssstretch → vorbis_rs, packed as .osz and opened with the shell. The TS UI only renders and sends commands.
 * Pin `osu-db = "=0.2.1"` (or its git rev) and add a regression test with an osu!.db header version of at least 20250107. `cargo add osu-db` silently picks the 2021 0.3.0 release, which cannot parse current databases.
 * Do not build rate changes on rosu-map's encoder. Write a text transformer that scales only the time fields (objects, hold ends, uninherited timing offsets and beatLength, PreviewTime, breaks, bookmarks, events) and copies every other line unchanged. Set a distinct Version string and a searchable tag (for example 'yourapp'), like osu!trainer does, so generated maps are easy to find and clean up.
 * Collections: never write collection.db while osu!.exe (or the Wine process) is running. Queue the changes, apply them when the process exits, and always keep a timestamped backup. Until then, show recommendations in your UI, and offer a search string (the tag) for song select in place of a collection.
 * Online data: use rosu-v2 with client credentials for search (q='keys=7', mode mania, then post-filter cs==7), stay under 60 requests/minute, and cache aggressively. Seed the recommendation corpus from the data.ppy.sh osu_files and mania_top_10000 dumps instead of crawling the API. Download .osz files through a mirror cascade with a proper User-Agent and Retry-After handling.
 * Dev environment: keep code in the WSL2 filesystem. Run osu! and tosu on Windows and reach tosu from WSL2 through mirrored networking or the host IP. Do real end-to-end tests on a native Windows build, since cargo-xwin cross builds are NSIS-only and 'last resort'. Add a Linux+Wine target later, using tosu's Linux build and TOSU_OSU_PATH.
 * AI vs algorithm, from the integration side: every signal available (per-column replay timing, judgement counts, MSD skillsets, pattern tags, rate) is structured and low-volume per user. Start with a deterministic, explainable weakness model: per-pattern accuracy deltas against expected accuracy at a given MSD/rate. Only add a learned model once you have a dataset. data.ppy.sh top-10k mania scores can calibrate expected accuracy per map.

The repo LICENSE says everything except interlude/ and online/ (GPLv3) is MIT, so the pattern engine can legally be ported. The report pointed to Companella's port instead. Source: https://github.com/
 + tosu v2 Play has a 'failed: boolean' field. It partly answers the open question about tracking failed plays without relying on Data/r. Source: https://raw.githubusercontent.com/tosuapp/tosu/master/packages/tosu/src/api/types/v2.ts
 + tosu binds 127.0.0.1 and whitelists ALLOWED_IPS by default (SERVER_IP / ALLOWED_IPS in tosu.env). This must be changed for WSL2 NAT access. Source: https://github.com/tosuapp/tosu/blob/master/packages/common/utils/config.ts
 + rosu-v2's current development happens on the 'lazer' branch, not main; the README recommends it as a git dependency. Source: https://github.com/MaxOhn/rosu-v2
 + rosu-pp has an unreleased 'pp-update' branch (last commit 2026-09-22) porting the 2026-07 official update. 4.0.1 does not reflect it (mania is unaffected). Source: https://github.com/MaxOhn/rosu-pp/tree/pp-update
 + The 2025-10-29 official pp/SR update is the one rosu-pp 4.0.0 ports; for mania it contains only a refactor. Source: https://osu.ppy.sh/home/news/2025-10-29-performance-points-star-rating-updates
 + rosu-storyboard (MaxOhn, 0.1.1) decodes and encodes storyboards and fills rosu-map's missing [Events] support. Source: https://crates.io/crates/rosu-storyboard
 + The osu:// protocol: osu://b/<beatmapId> and osu://s/<setId> open osu!direct for supporters and the website page for non-supporters. This partly answers the open question about jumping to a beatmap. Source: https://github.com/ppy/osu-api/wiki
